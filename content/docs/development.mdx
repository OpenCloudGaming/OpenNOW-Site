OpenNOW's active desktop client lives in `opennow-qt/` in the [OpenCloudGaming/OpenNOW](https://github.com/OpenCloudGaming/OpenNOW) repository, with Rust services under `native/`. This site is the canonical public documentation for that codebase. You do not need Node.js or npm to build or run the desktop app.

## Prerequisites

- Qt 6.8+ with Quick, Quick Controls 2, Multimedia, Network, Test, and ShaderTools
- CMake 3.24+ and a C++20 toolchain
- SDL3
- Rust/Cargo
- Platform media dependencies for the native streamer
- Linux: `pkg-config`, `libwayland-dev`, and `wayland-protocols` (required even for X11 builds), the `libva`, `libva-drm`, and `libdrm` development packages, and libclang; ARM64 Linux also needs the `libudev` development package
- A GeForce NOW account for end-to-end session testing

```bash
git clone --branch main https://github.com/OpenCloudGaming/OpenNOW.git
cd OpenNOW
cmake -S opennow-qt -B build/opennow-qt -DCMAKE_BUILD_TYPE=Debug
cmake --build build/opennow-qt
ctest --test-dir build/opennow-qt --output-on-failure
```

`main` matches the v1.0.3 release. Use `dev` instead of `main` for ongoing development. Point `CMAKE_PREFIX_PATH` at Qt and SDL3 when they are not already discoverable. The development executable is normally `build/opennow-qt/OpenNOW.exe` on Windows and `build/opennow-qt/opennow-qt` on Linux.

## Common commands

| Command | Purpose |
| --- | --- |
| `cmake -S opennow-qt -B build/opennow-qt …` | Configure the Qt app, core, and streamer FFI |
| `cmake --build build/opennow-qt` | Build the desktop app |
| `ctest --test-dir build/opennow-qt --output-on-failure` | Run Qt/C++ and related tests |
| `cmake --build build/opennow-qt --target opennow-ci-unit-tests` then `ctest --test-dir build/opennow-qt -L ci-unit --output-on-failure` | Run only the headless `ci-unit` Qt tests that CI runs |
| `cmake --build build/opennow-qt --config Release --target package` | Create CPack packages: WiX MSI and ZIP on Windows, DMG and ZIP on macOS, DEB on Linux |

The Qt CMake build compiles `opennow-streamer-ffi` with Cargo's release profile and links the resulting shared library into the app, including in Debug builds. On Linux it enables the bundled FFmpeg software decoder and native H.264 VA-API. There is no separate packaged streamer executable.

A direct developer CPack DEB uses the distribution's Qt and SDL3, so it needs Qt 6.8+ and SDL3 on the target system. Release DEBs instead bundle the AppImage runtime under `/opt/opennow`.

Repository JavaScript under `scripts/` is for tools such as localization checks (`npm run locales:check`). It is not required to build or launch the desktop client.

## Source layout

```text
opennow-qt/                  Qt Quick desktop app, C++ integration, and Qt tests
native/opennow-core/         Rust accounts, settings, catalog, and session services
native/opennow-streamer/     Native NVST transport, media, input, and Qt FFI
locales/                     English source and Crowdin-managed translations
docs/                        Architecture, protocols, acceptance, and release guides
scripts/                     Repository-only tooling (for example localization)
playnite/                    Playnite library integration (C#)
.github/                     CI workflows and contributor guidance
```

## Localization

UI strings live in `locales/en.json` as the English source file. Crowdin manages the other locale files. For translations, edit only `locales/en.json`. See the upstream contributing guide for the current locale workflow.

## Native streamer builds

For the Qt app, the streamer is built and linked through CMake/Cargo as an in-process library. The standalone `opennow-streamer` binary remains a development host and is not evidence for the packaged Qt presentation path.

See [Native Streamer](/docs/reference/native-streamer/) for runtime behavior, GPU integration, and diagnostics.

## CI and releases

Workflows in `.github/workflows/` on `main`:

| Workflow (file) | Trigger | Purpose |
| --- | --- | --- |
| `qt-ci` (`qt-ci.yml`) | Pull requests and pushes to `dev` or `main` that touch the app, native code, locales, or workflows; manual dispatch | Lint, packaging-contract and localization checks, then native tests on `linux-x64`, `windows-x64`, and `macos-arm64`. A manual run also builds all five package platforms. With `publish_nightly=true` it publishes a nightly prerelease with signed update manifests |
| `Qt checks` (`qt-checks.yml`) and `Qt unsigned build` (`qt-build.yml`) | Called by other workflows | Shared checks and package builds |
| `Qt Flatpak build` (`qt-flatpak.yml`) | Manual | Builds and checks an x86_64 Flatpak bundle and uploads it as an artifact. It creates no release |
| `qt-release-candidate` (`qt-release-candidate.yml`) | Manual, with an exact 40-character commit | Builds a signed production candidate: macOS Developer ID signing and notarization, optional Windows Authenticode, and isolated Ed25519 update signing. It does not publish a release |
| `Qt update-signed stable release` (`qt-stable-release.yml`) | Manual, on `main` | Promotes a successful `qt-release-candidate` run for the exact `main` commit to a public Latest release without rebuilding |
| `CodeQL Advanced` (`codeql.yml`) | Pushes, pull requests, weekly schedule | Code scanning |

Public Qt packages use names like `OpenNOW-Qt-<version>-…`. `main` now carries **v1.0.3**; each stable release is published from `main` through `qt-release-candidate` → `qt-stable-release`. Nightlies (`v1.0.3-nightly.<run>.<attempt>`) are published from `dev` by a manual `qt-ci` run with `publish_nightly=true`. They are prereleases and never replace the Latest release.

The v1.0.3 release contains Windows x64/ARM64 `-setup.exe`, `.msi`, and `.zip`; Linux x64/ARM64 `.AppImage`, `.deb`, and `.flatpak`; macOS Apple Silicon `.dmg` and `.zip`; two `.AppImage.zsync` sidecars; one `<asset>.manifest.json` per asset; `RELEASE-INFO.json`; and `SHA256SUMS`. Nightlies publish the macOS DMG only; their macOS ZIP is a CI validation artifact.
